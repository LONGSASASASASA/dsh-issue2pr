# 分析结论 · 目录约定

本目录存放针对代码库的**分析结论**(架构分析、缺陷诊断、方案论证等)。结论有时效性——它只对分析时所基于的代码版本成立。命名与头部约定的目的:让任何人在任何时候,一眼看出「这个结论是基于哪个版本得出的、后来有没有被推翻」。

## 文件命名

```
YYYYMMDD-序号-git短哈希-标题.md
```

例:`20260917-001-9d0ec6b-全局目标字段防节点跑偏分析.md`

| 段 | 规则 | 说明 |
|---|---|---|
| 日期 | `YYYYMMDD` | 分析完成日。放最前,文件名自然排序即时间顺序 |
| 序号 | 三位,`001` 起全局递增 | **不按日重置**——按日重置会产生两个 `-01`,跨日引用歧义;全局序号让每篇结论有唯一先后身份。新文档取目录内现有最大序号 +1 |
| git 短哈希 | 7 位 | 分析所基于的 commit。同一 commit 在不同分支是同一对象,故分支不进文件名、只写头部 |
| 标题 | 中文短标题 | 不含空格,人读检索用 |

## 文档头部(必须)

文件名里的短哈希只是索引,完整证据写头部元信息块:

```markdown
---
日期: 2026-09-17
编号: 001
基线: develop @ 9d0ec6b2d9c3d447444de1798c1ee0e76e42f96d
范围: lib/core/、lib/stages/
未提交改动: 无            # 分析时关键文件有未提交改动的,必须列出文件清单
取代: (无)               # 推翻旧结论时写旧文件名
状态: 有效                # 有效 | 已被取代
---
```

## 版本冲突防线

1. **结论只对基线版本负责。** 代码演进后旧结论可能失效,引用前先比对基线哈希与当前代码。
2. **取代必须双向标注。** 新文档头部写 `取代: <旧文件名>`;同时在旧文档头部补 `状态: 已被取代` 与 `被取代于: <新文件名>`。只写新不标旧 = 半年后两个"有效"结论并存。
3. **工作区不是版本。** 分析时若关键文件有未提交改动,头部必须注明文件清单;否则一律以 HEAD 为基线。
