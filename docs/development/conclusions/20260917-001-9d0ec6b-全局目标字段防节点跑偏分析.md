# 全局目标字段防节点跑偏分析

分析对象:issue2pr 流水线 P1-P11 的上下文传递链。核心问题:**是否需要定义一个贯穿全局的"目标"字段,防止节点跑偏。**

## 一、现状:意图传递链在中间断掉

### 1.1 各阶段实际拿到的上下文

逐阶段核对每个 LLM 调用的 user prompt 实际输入:

| 阶段 | user prompt 实际拿到什么 | 距原始目标 |
|---|---|---|
| P1 | issue 原文 | 0(即目标本身) |
| P2 | 01 契约 + 文件清单 | 1 跳 |
| **P3** | **只有候选文件源码**(`p3-code-understanding.js:20`) | **2 跳,完全看不到 issue 契约** |
| P4 | 只有 03 报告(`p4-hypothesis.js:31`) | 3 跳 |
| P5 | 只有 04 假设(`p5-planner.js:36`) | 4 跳 |
| P6 | 只有 05 任务图;builtin coder 更是只看到**单节点 + 单文件内容**(`p6-coder.js:230`) | 5 跳 |
| **P9** | coder-report + diff + test-report(`p9-reviewer.js:39`) | **审查者不知道 issue 要什么** |
| P11 | 01 + 04 + 07 + 08 + 补丁 | 末端才重新对表 |

### 1.2 三个典型断点

1. **P3 自相矛盾**:system prompt 要求"潜在修改点按与 Issue 目标的关联度排序"(`stageConfig.js:25`),但 user prompt 里根本没给 Issue 目标——模型只能靠文件名和内容猜关联。
2. **P9 只能审"干净",审不出"跑偏"**:三维门控是范围/安全/测试,一个方向完全错误但最小、干净、测试过的 diff 会顺利 pass。
3. **P11 是"事后验尸"不是"事中防偏"**:`ACCEPT` 对照 `success_criteria` 确实存在(`p11-pr-builder.js:98`),但到那里发现跑偏,代价是整条流水线已跑完、补丁已应用。

### 1.3 漂移机制

每一跳都是一次 LLM 有损变换(原文→契约→报告→假设→任务图→diff),5 跳之后原始意图只剩节点标题的字面残留;P5 节点的 `success_criteria` 是重新发明的,与 P1 标准之间**没有任何机器可校验的追溯链**;打回重跑只带 `reviewComment`,不带目标重申。

### 1.4 对偶风险:无防护地注入 goal 会诱发扩权

防跑偏不能简单等于"每阶段都塞 goal":LLM 面前同时放着全局目标和局部任务单时,若两者有张力(任务单只改一个文件、目标看似需要改三个),模型可能"好心"扩大修复范围。两种失败模式代价不对称:

| 风险 | 只传 task(漂移) | 无防护传 goal(扩权) |
|---|---|---|
| 发生方式 | **静默**——task 看似完整,方向错无人知 | **可见**——diff 里明摆着多改了文件 |
| 谁能发现 | 只有 P11 末端验收 | P9 范围维 / 派单文件白名单 |
| 代价 | 全流水线重跑(补丁已应用) | 打回 P6/P5 重做 |

设计目标因此是:**在产生方向的节点用 goal 防漂移,在执行节点用 task 锁边界,并用机制保证两者不互相侵蚀**。另有一个反直觉事实:没有 goal 时模型会自行脑补"完成判据"(防御性代码、顺手重构),goal 恰恰提供"达标即停"的信号——注入得当时是收窄而非扩大实际改动范围。

## 二、优化方法

### 2.1 核心原则

1. **goal 是判断依据,不是行动授权**。它回答"方向对不对、做到什么程度算对",不回答"要不要多做几件事"。行动授权只来自 task 节点/派单。
2. **单一来源,禁止二次加工**:goal 只由 P1 产出,P2 起只读注入;任何阶段"重述目标"都是二次漂移源,不引入额外 LLM 调用。
3. **按节点角色分层注入**,而非全线统一(见 2.2)。
4. **边界声明由投影函数统一注入**,不靠各 prompt 手写,保证全流水线口径一致。

### 2.2 节点分层:谁要 goal,谁只要 task

按"该节点做不做方向性判断"划分:

| 节点 | goal 形态 | 理由 |
|---|---|---|
| P1 | **生产者** | goal 的唯一来源,不存在注入问题 |
| P2 | 无需改 | 现在就消费 01 全文(`p2-search.js:32`),已是 goal 直接消费者 |
| **P3** | 完整投影 | "修改点按 Issue 关联度排序"是方向性排序 |
| **P4** | 完整投影 | 假设筛选 = 对照 criteria 判断"哪个才值得修" |
| **P5** | 完整投影(**最关键**) | 拆分本身是方向决策:保证 nodes ⊆ goal 且 ∪nodes ≈ goal,防拆偏就在这一跳 |
| P6·planner(派单) | 完整投影 | 节点→文件归属是方向性映射 |
| P6·coder(builtin) | **task 为主 + 一句背景** | 物理上只见派单单文件(`p6-coder.js:227`),goal 价值仅剩消歧义,扩权风险却集中在此 |
| **P6·委外**(session/claude/dsh) | 完整投影 + 强边界声明 | 与 builtin 相反:委外 agent **看得见全仓库**,自主性强、脑补空间大——goal+边界组合的价值在这里最高;不传 goal 它也会扩权(自主性所致,非 goal 引入) |
| P7 / P8 | 无 | 纯机械,无 LLM |
| **P9** | 完整投影 | 审"干净"看 diff,审"解决没解决"必须对照 goal |
| P10 | 无 | 失败分类是技术判断(超时/环境/协议),与目标无关 |
| P11 | 现状不变 | 已消费 01 全文 |

规律:**产生方向或审查方向的节点给 goal,执行方向的节点只给 task**。P6 内部三角色(planner/coder/委外)不同待遇,是本设计的精度所在。

### 2.3 goal 怎么生成

1. **P1 schema 扩展两个字段**:
   - `goal`(必填,一句话):写法约束进 P1 prompt——动词开头、含对象模块、含可判定完成状态。例:"修复 X 场景下 Y 抛错,使 Z 测试通过"。
   - `non_goals`(可选,数组):明确不做什么,直接服务防扩权。
2. **`goalBriefOf(rcx)` 机械投影**(`helpers.js`):goal + success_criteria + constraints + non_goals + 一段**固定边界声明文案**("执行范围以任务节点/派单为准;节点/派单之外发现的问题,一律记录上报(no_change reason 或报告字段),不得自行修改")。边界声明统一注入是防扩权的机制落点。
3. **旧 run 兼容**:无 goal 字段时由 phenomenon + scope 兜底拼接;各阶段每次读盘注入,天然满足"只随 P1 重跑而变"的不可变语义。
4. **质量守门注意**:P1 不是 key 阶段(`pipeline.js:20`),`key-only` 模式下 goal 无人复核——schema 必填 + prompt 写法约束是唯一防线,实施时需验证 P1 产出稳定性。

### 2.4 尺寸控制:条数为主,2K 硬顶,截断标注

初版方案的"1K 字上限"过粗,**字符是错误的控制单位,条数才是**:

- 条数上限:criteria ≤8 / constraints ≤8 / non_goals ≤5 / scope ≤10;超限截断并在尾部标注"已截断 N 条"——与项目诚实原则同口径(P9 diff 节选标注、`buildDelegateTask` 的截断先例)。
- 2K 字符硬顶仅防"P1 写小作文"。成本占比:P3 单次 36K 字注入占比 ~5%,P9 约 18K 字占比 ~10%,P6 coder 轻量形态 ~150 字占比 ~2%——瓶颈不是 token 预算而是**信噪比**,goal 块越长每条判据被注意力稀释越多。
- **流程信号**:若 8 条 criteria 都装不下,通常不是投影预算太小,而是**该 issue 应拆成多个 run**(一 run 一目标)——不应靠放大投影掩盖。

### 2.5 实施分级

**第一步(小改、零 schema 变更、纯增益)**:
- `helpers.js` 加 `goalBriefOf(rcx)`;
- 分层注入:P3 / P4 / P5 / P6·planner 用完整投影;P6·coder(builtin)用一句背景 + 边界声明;`buildSessionTask` 与 `delegateExternal` prompt(`p6-coder.js:35`/`p6-coder.js:62`)注入完整投影 + 强边界声明。

**第二步(委托模式补齐)**:P3-P5、P9 的 `delegateSpec.inputs` 同步加 01——否则委外智能体与本机看到的目标不一致,等于白改。

**第三步(机制级,单独评估再动)**:
- P9 增加"需求符合度"维度:动 `08-review-report` 契约、P11 的 `DIFF` 判定与 `delivery.js` 消费,存量 run 报告需兼容,建议前两步落地观察后再决策;
- P5 节点增加 `criteria_trace` 字段,形成对 P1 标准的机器可校验追溯;
- P7 应用补丁时校验 **diff 涉及文件 ⊆ 派单文件清单**,越界显式失败并指引回 P5 重规划——把"扩权"从"审查可能漏"变为"流水线必然拦";需留合法例外通道(修复确需改派单外文件时打回 P5 把节点拆对,而非让 coder 先斩后奏)。

### 2.6 不建议做的

- ❌ 新开一个"目标管理"阶段——过度设计,01 已是权威载体;
- ❌ 各阶段输出中重新生成/改写目标字段——二次漂移源;
- ❌ 把 01 全文塞进每个阶段——防膨胀会失败,投影必须瘦身;
- ❌ 全线统一注入(含 P6·coder 用完整投影)——把扩权风险错误地引入执行层。

### 2.7 验证指标

落地后观察:P11 `ACCEPT` fail 率、P9 打回率、diff 越出派单文件清单的频率、复核打回意见中"答非所问"类反馈占比。
