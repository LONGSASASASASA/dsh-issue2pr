# 修复任务清单 20260916-001

## 目标

本轮仅处理以下三类问题：

- 内置 LLM 协议可靠性。
- 内置 LLM、Claude Code 自动委外 Agent、DSH 原生 Agent 的全过程可追溯性。
- P11 / P10 失败分类准确性。

交付标准：**完整保存系统实际可观测到的输入、输出和执行事件；准确关联阶段执行、逻辑调用和实际重试；明确结束状态、失败原因和留档完整性。平台未暴露或未成功持久化的内容必须明确标记，不推测、不补造，也不能伪装成业务验收失败。**

## 勾选规则

每个 Task 的实现、对应测试和验收条件全部完成后，才将该 Task 的 `- [ ]` 改为 `- [x]`。不得因只完成部分子项而提前勾选。

## 本轮明确不处理

- P1 → P6 需求偏离修复。
- 业务规划规则调整或新增需求推导规则。
- 悬浮助手日志扩展。
- 自动日志清理或历史日志删除策略。
- 人工独立启动会话的自动完整采集。
- 留档磁盘预算量化与容量治理（本轮不估算、不设上限）。
- 留档内容明文敏感性与脱敏（保真优先，不做脱敏）。

人工接管仅记录系统能观察到的任务交接和产物，不宣称已采集人工独立会话中的全部交互。

## Task 清单

- [x] **TASK-01：建立统一调用身份与关联模型**

  实现要求：

  - 为一次阶段执行生成稳定的 `stageExecutionId`，明确区分阶段重跑。
  - 为一次逻辑 LLM 调用生成 `callId`。
  - 为每一次真实模型请求生成独立 `attemptId`。
  - 同一逻辑调用的所有重试共享 `callId`，记录 `attempt`、`retryOf`、重试原因。
  - `retryOf` 指向前一个实际请求的 `attemptId`，避免把阶段重跑与模型重试混为一类。
  - 委外执行继续保留 `captureId`，并关联 `runId`、`stage`、`stageExecutionId`。
  - 防止历史记录、迟到响应或旧 capture 混入新的阶段执行。

  验收条件：同一阶段重跑、同一调用重试、多次委外执行都能通过身份字段明确区分并反向关联。

- [x] **TASK-02：完整记录内置 LLM 的实际请求、响应和结束元数据**

  实现要求：

  - 请求发送前持久化实际传入宿主的 system、messages / user prompt。
  - 保存实际生效的 provider、model、reasoningEffort、maxTokens、timeout 等允许字段。
  - 不序列化 API Key、认证对象、请求头、环境变量或其他认证信息。
  - 响应过程中持续追加保存宿主实际暴露的文本及其他响应事件。
  - 保存原始 finish reason、归一化 finish reason、usage、耗时和结束状态。
  - 保存 JSON 提取、解析、schema 校验等处理错误及其原文引用。
  - 覆盖普通文本 `complete()`、结构化 `completeJson()` 和 P10 的模型调用。

  验收条件：从 `callId` / `attemptId` 能回溯一次请求的实际输入、响应正文、结束原因、usage 和处理结果，摘要日志中不混入完整正文。

- [x] **TASK-03：实现通用持续写盘、日志轮转、原文引用和完整性状态**

  实现要求：

  - 使用有界写入缓冲持续写盘，达到文件大小阈值后切换新分片。
  - 轮转只负责分片，**不得因轮转截断或删除历史内容**。
  - 维护分片清单和读取顺序。
  - 原文引用统一包含 `path`、`offset`、`length`、`sha256`、`encoding` 等必要字段。
  - JSON 记录尽量不跨分片；超大单条记录允许使用独立大文件。
  - 请求状态、结果状态和索引文件使用原子更新。
  - 执行期间就更新状态，异常退出后可以区分“未观察到正常结束”。
  - 日志完整性作为一等字段，至少支持：`complete`、`partial`、`unavailable`、`write_failed`、`corrupt`。
  - 不通过“文件是否存在”间接推断留档完整性。
  - 请求尚未发出且请求快照无法持久化时，中止该调用并明确报出留档故障。
  - 请求已经发出后发生写盘失败时，完成必要收尾，同时标记 `partial` / `write_failed`；不得伪装成完整留档。
  - 状态或索引写入失败不得覆盖原始业务异常，两类错误都要保留。

  验收条件：轮转、异常退出、写盘失败、索引损坏、缺失分片、跨 UTF-8 边界和超大消息都能得到明确且可诊断的结果。

- [x] **TASK-04：重构结构化输出处理顺序和稳定错误分类**

  固定处理顺序：

  1. 保存响应正文、响应事件和结束元数据。
  2. 判断调用失败、取消、超时或输出截断。
  3. 提取目标 JSON。
  4. 执行 `JSON.parse()`。
  5. 执行 schema 校验。
  6. 执行业务门禁判断。

  稳定错误类别：

  - `llm_call_failed`
  - `output_truncated`
  - `json_parse_failed`
  - `schema_validation_failed`
  - `business_gate_failed`

  其中 `llm_call_failed` 继续保存 timeout、provider、cancelled 等具体原因。明确的 token / length / incomplete 结束原因优先判定为 `output_truncated`；即使返回文本碰巧能够解析，也不能当作完整成功结果。

  验收条件：同一输入在不同失败位置得到稳定、互斥且可序列化的错误码，原始响应和 finish reason 始终可回溯。

- [x] **TASK-05：为所有现有结构化调用补齐 schema**

  实现范围：

  - P1。
  - P2。
  - P4。
  - P5。
  - P6 Planner / Reviewer。
  - P9。
  - P10。
  - P11。

  校验至少覆盖必填字段、对象与数组类型、数组元素类型、枚举和必要嵌套结构。P11 严格校验 `ROOT`、`DESC`、`ACCEPT` 和 `reasons`。

  本 Task 只固化现有输出契约，不新增需求推导逻辑，不改变任务规划或编码方向。

  验收条件：缺字段、错误类型、非法枚举、错误嵌套均稳定返回 `schema_validation_failed`，已有合法输出继续通过。

- [x] **TASK-06：重做结构化调用的有限重试机制**

  实现要求：

  - 默认一次逻辑调用最多 2 次真实模型请求，所有错误分支共用这个总上限。
  - 每次实际请求独立使用 `attemptId` 留档，最终错误保留完整 retry chain。
  - JSON / schema 错误的第二次请求仅携带目标 schema、具体错误和上次原始响应，使用独立的格式修复指令。
  - 格式修复不得再次发送原业务长 prompt。
  - 输出截断时允许在明确预算上限内提高一次输出预算后重试，并记录实际生效预算。
  - timeout、provider 服务错误和有效业务 `fail` 不进入格式修复重试。
  - 无法恢复业务内容时保持失败，不补造结论。

  验收条件：首次非法 JSON 可在第二次格式修复成功；连续失败时错误码和重试链正确；总请求次数及输出预算均受限。

- [x] **TASK-07：贯通结构化错误对象并修正 P11 / P10 失败分类**

  实现要求：

  - 流水线不再仅保存异常字符串，同时保存可序列化结构化错误。
  - 错误对象至少保留 `code`、`message`、`stage`、`callId`、`attemptId`、`cause`、`finishReason`、`logRefs`、`retryHistory`。
  - 结构化错误进入运行状态 / failure context，重启后仍可被 P10 确定性读取。
  - P11 协议错误时保持 `ACCEPT = null`，保留有效的 PATCH / TEST / DIFF 客观门禁证据。
  - P11 协议错误时禁止复用历史通过结果。
  - 只有拿到有效业务结论 `fail` 时，才进入业务验收失败路径。
  - P10 对模型输出协议错误、模型调用超时、模型服务错误等使用系统确定性分类。
  - P10 的 LLM 仅可补充解释和建议，不得覆盖系统已经确定的失败类别。
  - P10 自身再次失败时，必须继续保留原始诊断和原始日志引用。

  验收条件：P11 协议错误、模型调用错误和真实业务验收失败在运行状态与 UI/API 数据中保持不同类别；重启后分类不丢失。

- [x] **TASK-08：补齐 Claude Code 自动委外全过程留档**

## 核心回归场景

- 完整长 prompt / response 可以通过 `callId` 回溯，摘要中没有混入全文。
- 流式异常、timeout、cancel、子进程强制终止后，已持久化内容仍可恢复。
- JSON 首次非法后格式修复成功；连续失败时最终错误码准确。
- 字段类型、枚举、嵌套结构非法得到 `schema_validation_failed`。
- length / token 限制得到 `output_truncated`。
- 重试总次数和输出预算有上限。
- 格式修复不重复发送原业务长 prompt。
- P11 协议失败清除历史通过状态，并保持 `ACCEPT = null`。
- 结构化错误落盘并重新加载后，P10 分类仍正确。
- Claude stdout / stderr 超过旧限制后仍完整可恢复。
- 轮转、跨 UTF-8 分片、超大消息和多轮执行均可追溯。
- DSH 执行未结束时已有事件落盘，正常收尾不重复记录。
- 写盘失败、索引损坏、缺失分片明确报错。
- 旧格式日志仍可读取。
