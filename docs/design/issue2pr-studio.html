00 · PRODUCT CHARTER

产品总纲

Run Console 是核心工作界面，Agent 是可替换执行器， Evidence 是核心数据资产。

核心能力

需求标准化软件交付状态机执行器编排 证据链策略门禁人工介入

四层职责与模块契约见第 02 章； 用户角色和交付边界见第 01 章。

核心原则
执行器可替换，模型可替换，会话可重建； Run 的已确认状态与关键证据，由 Issue2PR 独立持久化和管理。

执行器中断后，控制台仍应展示已保存的任务、变更和验证记录， 明确中断原因、待核对信息与恢复条件。

交付证据主线

需求 / Issue → WorkItem → Task → Diff → Test → Review → PR 交付包或无变更结论

这条主线说明目标、工作和证据之间的关联。 真实 PR 发布在明确授权后执行，并独立记录结果；完整阶段与门禁见第 06 章。

用户价值

用户能够同时看见执行器正在做什么、代码库发生了哪些真实变化， 以及这些变化是否满足原始需求。

01 · Product Definition

从一次软件变更，到可验收的交付

以研发操作者为主要日常用户，明确需求提出者、Reviewer 与项目负责人的分工，界定一次运行的交付结果。

核心对象是 Software Change Run（软件变更运行实例） 。需求或 Issue 经标准化后进入 Run，系统编排可替换的 Coding Agent，并用真实仓库状态、版本化产物和验证记录推进流程。最终交付包含代码、证据、风险说明和验收结论。

目标明确

Issue 与需求文档分流理解，汇合为统一契约；验收草案、业务边界、非目标和未知项显式保存。

结果可信

任务完成、代码合法、验证通过、审查通过分别判定；最终结果与实际候选版本一致。

过程可控

自动推进有范围和预算约束；关键决策可人工介入，中断后仍可恢复并追溯历史。

02 · System Architecture

四层系统架构

系统由 UI、Control Plane、Evidence & State、Executor 四层及十六个模块组成。各层通过任务、证据与权限契约协作。

谁决定状态

Workflow 与 Gate 读取有效证据作出决策。Agent 的文字结论不能直接推进 Run。

谁证明变更

系统从真实 worktree 和冻结候选采集 Git 事实；执行日志与测试结果保留原始来源。

谁控制权限

Policy 明确范围、工具和网络权限；Human 操作也被记录、鉴权并绑定所批准的版本。

一个需求拆成多个工作项时

S0 提出候选边界，S1 核对仓库与依赖，S2 确认独立交付和验收的可行性。前端、后端和数据层通常是同一工作项下的 Task，不按技术层机械拆分。确需拆分时，保留父需求全部必需 AC、各项归属、依赖契 约版本与组合验收；任何必需子项或组合验收尚未完成，父需求都显示“部分完成”。

已确认的协调边界 · D03

一个 Run 绑定一个仓库和一个 PR 目标；跨仓库需求由多个工作项协调。依赖方绑定上游候选或合入版本，上游变化触发重新检查；跨 PR 的发布或合并顺序必须显式声明。

5.5 · 四种来源，不混同为已确认事实

表 11 字段来源与证据边界
来源类别可以说明什么不能替代什么
source_statement · 原文陈述提交者表达的目标、规则或报告的现象；记录精确位置。原文中猜测的根因不能替代复现或仓库证据。
model_inference · 模型推断推导理由、假设和需要验证的候选解释。不得直接升级为关键业务规则、授权或通过结论。

5.6 · 从一句业务诉求到可实施的工作项

员工可以在线提交报销申请，超过一定金额需要财务复核。

S0 · 先理解业务

提取员工、财务、提交报销与条件复核。列出金额阈值、复核顺序、退回和重新提交等待确认规则。

S1 · 有边界地分析

只读核对现有报销、身份权限、流程与数据能力；标注差距。阈值未定时，不把推测写成业务规则。

S2 · 确认后工程化

关键问题闭环后形成验收基线、任务、技术范围与 Test Plan，再通过实施门槛。

验收草案可以写为“满足已确认复核条件的申请必须进入财务复核”，同时关联阈值与流程问题，明确当前尚不可作为最终可执行验收。系统不能自行填写金额阈值。

前端、接口与数据改动通常是同一工作项下的任务。只有能够独立验收、交付且依赖明确时才拆成多个工作项；父需求仍保留完整 AC 和必要的组合验收。附录给出带阻断问题的需求草案示例。

06 · Delivery Pipeline

八阶段主流程，按证据完成交接

八阶段描述 Run 的交付生命周期。S3 内部可以有多个 Task 与 Attempt；局部验证服务于实施，S4 / S5 / S6 负责最终组合候选的正式验收。Failure Router 是横贯各阶段的控制能力。

没有代码变更时如何走完流程

S3 产出 no_change 结果后，S4 确认真实无变更，仅对不适用的补丁检查记录原因；S5 仍验证目标行为，S6 审查结论。S7 保存无变更交付结论并结束 Run，不要求生成空 Patch 或空 PR。

每次交接都满足 前置条件 → 执行 → 版本化产物 → Validator → Gate。阶段进行中、执行器结束、门禁通过是不同状态；UI 不能用“Agent 已完成”替代正式通过。

07 · Task Execution & Integration

局部任务完成，最终组合仍要验收

Task 定义要达到的目标，Attempt 记录具体执行，Candidate 表示最终组合结果。只有这三者的输入、产物和引用都明确，才可以复用任务成果并可靠处理失败。

计划、调度与集成约束

  • 每个 Task 声明目标、必需性、依赖、AC 映射、允许范围、预期结果类型和验证方法；依赖图必须无环。
  • 同一可写工作区只允许一个活动写入者。独立任务可在隔离工作区并行；存在依赖时，消费者必须绑定已接受的上游结果版本。
  • 每个 Attempt 绑定基线与输入引用；执行过程中产生的真实 Diff、工具活动、局部测试和预算消耗均归属于该 Attempt。
  • 按依赖关系集成已接受的任务结果。冲突进入明确的集成修正任务或新 Attempt；冲突解决本身也是需追踪的变更，不能静默改写原证据。
  • 冻结 Candidate 后执行正式 S4 / S5 / S6。测试工具若修改源代码或配置，应使候选失效；批准的构建输出与源代码分开记录。
  • 上游任务更新后，重算依赖任务的基线与结果有效性。无关任务的局部证据可以保留，但代码组合变化必须刷新候选级验收。
验收必须双向闭合

方向一：每一处最终变更都有 Task 与 AC 或获准的工程约束作为依据。方向二：每一项必需 AC 都有有效完成结果和验证证据。只检查“已接受 Task”会漏掉尚未完成的必要工作。

保存事实，重建状态，精准传播失效

9.2 · 证据可信度与版本身份

产物元数据至少记录 schema_version 、内容哈希、输入引用及哈希、仓库基线、候选代码树、环境指纹、配置哈希、策略版本、执行器及版本、Prompt 版本和采集时间。Agent 报告是候选说明；测试命令、退出码和日志由受控 Runner 采集 ，正式证据区不向代码执行器开放写权限。

真实执行与业务正确性分别证明

测试确实运行，只能证明所执行检查的结果。系统还必须检查测试计划是否覆盖必需 AC，以及测试本身是否被无依据地削弱。证据可核对、可审计，但不使用“绝对不可伪造”作为产品承诺。

9.3 · 一致性与恢复协议

  • 产物先写临时对象并校验内容，再原子提交；发布带产物引用的事件后更新状态投影。孤立临时对象不能被视为阶段成功。
  • Event Log 追加写入，包含唯一事件 ID、顺序、Run / Task / Attempt、来源、关联命令和时间。消费者按游标补齐与去重。
  • 同一 Run 的推进由单一有效控制者负责；通过租约或等价 fencing 机制拒绝失效控制者的写入与状态更新。
  • 重启时先重建状态，再核对活动执行器、工作区及尚未确认的外部操作。未确定是否停止的执行器不能直接启动第二个写入者。
  • 只复用输入指纹匹配且已验收的结果；中断的 Attempt 保存最后快照，新的执行产生新 Attempt 并引用前次失败上下文。
  • 创建 PR 等外部操作有稳定请求标识和回执；响应丢失时先核对远端状态，确认后补记结果，禁止事件重放直接重复产生副作用。

not_applicable交付为无需代码变更的结论 不发起 PR 发布，也不计作发布失败。
三个状态可以同时成立

run_status = completed、delivery_status = ready_for_pr、 publication_status = failed 表示变更已验收，但真实 PR 发布失败。 用户仍可导出有效交付包；重试成功后仅将发布状态更新为 pr_published。 无变更成功则记录 completed / completed_no_change / not_applicable。

completed / failed / cancelled 是运行终态。未结束的 Run 可以按规则恢复或回退； 已结束后若需重新执行 S0—S7，创建关联的新 Run，并复用指纹匹配的有效产物。 发布重试不创建新的软件变更 Run，也不重复计为一次交付。

已交付后发生变化时，重新判定 delivery_status；结果失效标为 stale， 不改写原 Run 的结束事实。发布操作绑定交付版本、候选与目标，历史回执保留： 即使曾经 pr_published，当前交付失效后也不能继续显示“当前版本已验收”。

Ready for PR 的完整定义

当前工作项、分析、计划、Scope 与 Test Plan 有效；关键问题已闭环；所有必需验收项和必要任务都有完成证据；最终候选 S4 / S5 / S6 满足交付策略；代码与证据一致，描述忠实，审批有效，当前引用集合无 stale 产物或未解决 blocking finding。允许的豁免独立显示；历史中的 stale 产物保留，不妨碍当前有效交付。

真实发布的失败与重复操作

  • 创建或更新 PR 必须在明确授权范围内执行；授权绑定候选、目标与操作类型，代码变化后重新判断授权是否有效。
  • 网络超时、响应丢失或控制面重启时，先用稳定请求标识与远端状态核对是否已完成；确认未执行后才重试。
  • 已确认发布失败时，按状态转移表记录独立结果。 重试前核对候选与授权，不重复执行 S0—S7。
  • PR 被他人加入新提交、目标变化或远端结果不一致时，重新核对交付有效性；失效则将 delivery_status 标为 stale。历史发布回执保留，不能用曾经 pr_published 声称当前 PR 已验收。
  • 本地代码回退只恢复隔离工作区。撤回、更新、关闭远端 PR 或合入后回滚，需要单独授权与对应回执。
